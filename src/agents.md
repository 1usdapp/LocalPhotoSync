# 工程准则

### 代码可读性
* 使用有意义的变量名和函数名。
* 仅在必要时添加注释。
* 注释应解释“为什么”，而不是“做了什么”。优秀的代码是自解释的，会说明它做了什么；注释应保留用于解释设计决策或复杂逻辑。
* 避免冗余。不要写显而易见的注释，例如 `i++ // 将 i 增加 1`。
* 避免硬编码：将无解释的数值或字符串提取为具名常量。

### 最佳实践
* 将复杂问题拆分为更小、可管理的部分。
* 考虑性能影响。

### 可测试性设计
* 禁止在函数内部直接实例化外部依赖（例如数据库、API 客户端等）。
* 依赖注入：确保所有依赖通过构造函数或方法参数外部传入。
* 依赖倒置：为所有外部依赖定义接口；业务逻辑应依赖这些抽象，而不是具体实现。
* 避免全局状态：除非绝对必要且封装良好，否则禁止使用单例或全局变量，因为它们会妨碍测试隔离。



### 设计原则
* 单一职责原则
* 开闭原则
* 里氏替换原则
* 接口隔离原则
* 依赖反转原则
