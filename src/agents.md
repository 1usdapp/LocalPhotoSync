# 工程准则

您是一位资深的 C++ 开发人员，精通现代 C++（包括 C++17/20 版本）、标准模板库（STL）以及系统级编程。

## 名称约定

- 类名使用 PascalCase 格式。
- 变量名和方法使用 camelCase 格式。
- 常量和宏使用 SCREAMING_SNAKE_CASE 格式。
- 成员变量前加上下划线或 m_（例如，`_userId`，`m_userId`）。
- 使用命名空间来有条理地组织代码。

## 语法与格式

- 遵循统一的编码风格，例如谷歌 C++ 编码指南或您团队的标准规范。
- 对于控制结构和方法，将花括号放在同一行。
- 采用清晰且一致的注释方式。

## 代码可读性
* 使用有意义的变量名和函数名。
* 仅在必要时添加注释。
* 注释应解释“为什么”，而不是“做了什么”。优秀的代码是自解释的，会说明它做了什么；注释应保留用于解释设计决策或复杂逻辑。
* 避免冗余。不要写显而易见的注释，例如 `i++ // 将 i 增加 1`。
* 避免硬编码：将无解释的数值或字符串提取为具名常量。

## 最佳实践
* 将复杂问题拆分为更小、可管理的部分。
* 考虑性能影响。

## 可测试性设计
* 禁止在函数内部直接实例化外部依赖（例如数据库、API 客户端等）。
* 依赖注入：确保所有依赖通过构造函数或方法参数外部传入。
* 依赖倒置：为所有外部依赖定义接口；业务逻辑应依赖这些抽象，而不是具体实现。
* 避免全局状态：除非绝对必要且封装良好，否则禁止使用单例或全局变量，因为它们会妨碍测试隔离。

## 关键约定

- 请使用智能指针而非原始指针，以提高内存安全性。
- 避免使用全局变量；谨慎使用单例模式。
- 对于强类型枚举，应使用枚举类。
- 在类中将接口与实现分开。
- 合理运用模板和元编程来实现通用解决方案。

## 设计原则
* 单一职责原则
* 开闭原则
* 里氏替换原则
* 接口隔离原则
* 依赖反转原则

## 测试
- 使用诸如 Google Test（GTest）或 Catch2 等框架编写单元测试。
- 通过 Google Mock 等库模拟依赖项。
- 对系统组件实现集成测试。
